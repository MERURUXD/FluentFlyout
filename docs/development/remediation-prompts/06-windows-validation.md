# 整改阶段 6：Windows 验收与测量

请在 `MERURUXD/FluentFlyout` 执行本阶段，验证前序整改后的真实行为和性能。不要在验收期间继续加入优化、清理依赖或调整音质/视觉效果。

## 先读与准备

- `AGENTS.md`、`docs/development/remediation-prompts/README.md`，以及阶段 1–5 的实际交付和未测项。
- `docs/development/baseline.md` 的测量约定、当前 performance、architecture、downstream-policy、release 文档。
- 确认待验收 commit、对照 commit、构建配置/版本、产物来源及测试命令。参考审查 SHA 只是可选对照，必须确认它适合本次比较，不重置用户分支。
- 必须使用得到授权的 Windows 桌面与受控测试账号/配置；纯 Linux 环境或非交互 CI 不能替代。若没有环境，交付可执行的测试清单与阻塞信息，不填造结果。
- 使用临时目录、测试配置和备份；不要写入真实上游设置、暴露用户媒体/日志、使用生产凭据，或未经允许修改用户启动项/设备设置。需要重启、切换设备等有影响的动作时先确认权限。

## 功能与生命周期验收

1. **两种禁用路径都测。**
   - 从未开启任务栏、可视化或音量消费者的冷启动。
   - 开启后关闭最后一个消费者；再重复启停，验证对应 timer、capture、订阅和窗口停止/释放。
   - 仍有共享消费者时不能误停它的资源。
2. **并发和恢复。** 设备切换、锁屏恢复、Explorer/显示环境恢复与功能关闭交错；主浮窗和任务栏高频更新时关闭/重建任务栏。结合前序确定性回归测试，检查是否有孤立 capture、隐藏窗口增长、异常和失效回调。
3. **媒体选择。** Spotify/浏览器播放暂停组合、过滤、Automatic/未知值、新增未选中会话、相同 metadata 的同 ID 关闭重启，以及 Next Up、音量和控制目标的一致性。把依赖的已知原地替换限制单独记录。
4. **设置与身份。** 用可丢弃的设置 fixture 验证新装、旧设置迁移、备份恢复、显式功能值和下游身份；原文件保持不变。正式上游安装的共存测试需受控环境，不使用用户主配置试验。
5. **网络与更新。** 自动化测试使用本地响应/fixture；若进行真实网络验证，只在受控环境观察本进程的请求目标，验证没有上游遥测/实验/更新请求。区分允许的下游元数据请求与用户主动外链，不声称产品完全离线。
6. **产物。** 解包确认版本、SHA、源码入口和许可材料；未支持的 MSIX 安装、Store、签名、正式发布仍不在本阶段自动授权范围内。

## 性能比较

- 对照和待验收版本使用同一台机器、相同 Windows build、电源模式、显示/缩放、媒体源、构建配置和功能设置；分别构建到独立目录。
- 至少覆盖：无播放全关、固定媒体播放全关、仅任务栏、任务栏加可视化、音量消费者开启，以及对应功能开启后再关闭。
- 按 baseline 约定每场景进行五次冷启动，固定稳定等待时间和 60–120 秒采样窗口；无法保证冷启动或同条件时明确标注，不能混为可比数据。
- 记录启动就绪时间、CPU 均值/峰值、Working Set、Private Bytes，以及相关周期唤醒、capture/窗口数量。写清指标定义、采集方法和 units。
- 保存逐次原始数据及必要脱敏证据，再给汇总。没有测量就不声称某个百分比改善；没有统计依据就不把噪声解释成收益。
- 真实用户数据和大体积 trace 不默认提交到仓库；仓库里只放适合公开、可复核的说明/小型脱敏结果。其他证据交付到用户指定的安全位置。

## 验收与交付

- 先运行前序自动化回归测试、AGENTS 的构建/格式与最终差异检查，再记录真实桌面结果。
- 对每个场景标记通过、失败、未测或受依赖限制，并附准确版本、复现步骤和证据；不能用“构建通过”替代 GUI、音频或网络结论。
- 发现问题时回报到对应修复阶段，给出最小复现与严重性，不在本阶段悄悄扩大实现范围。
- 最后分别判断：功能是否正确、关闭是否释放、性能数据是否可比，以及哪些后续优化才有依据。不要因为验收完成就合并、发布或移动 tag。

按共用格式交付并停止。本阶段不自动启动新一轮优化。
