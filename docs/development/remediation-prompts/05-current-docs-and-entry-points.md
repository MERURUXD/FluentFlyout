# 整改阶段 5：当前文档与下游入口

请在 `MERURUXD/FluentFlyout` 执行本阶段。以已经实现并验证的行为为准统一文档，不为了使旧文档看起来正确而改变运行时，也不把计划中的修复写成完成状态。

## 先读与核验

- `AGENTS.md`、`docs/development/remediation-prompts/README.md`，以及阶段 1–4 的实际改动和验证结果。
- `docs/development/` 下的 baseline、architecture、downstream-policy、performance、release 文档。
- `README.md`、所有 `README.*.md`、`PRIVACY-POLICY.md`、`CODE_OF_CONDUCT.md`。
- `.github/CONTRIBUTING.md`、`.github/ISSUE_TEMPLATE/`、`.github/pull_request_template.md`、CLA 和 MSIX 工作流。
- 相关产品身份、更新、遥测、实验、设置默认值/迁移、窗口/资源生命周期实现。

## 要做的事

1. **区分历史、当前规则与验证证据。**
   - 保留 baseline 的历史基线意义，不回写成当前状态。
   - architecture 作为当前架构说明，消除“Stage 1 尚未隔离”等过期描述，纠正启动路径、身份/配置目录、默认值和生命周期。
   - 保持 AGENTS 简短，链接具体说明而不复制多份事实；其长期规则不能变成阶段进度表。
   - performance 区分目标、代码确认、自动化和实际测量。没有桌面测量就不写性能百分比或“关闭后零资源已证明”。
2. **统一用户入口而非重译上游。**
   - README 语言入口使用仓库内相对链接；每份语言 README 至少有明确的下游提示、下游发布入口和上游参考说明。
   - 无可靠翻译时用简短、准确的公共提示，不生成大量未经校对的翻译。保留上游署名、致谢和明确标注的参考信息。
   - 描述当前 ZIP/dev/stable 支持范围，不能让未支持的 MSIX、Store 或 ARM64 入口看起来是已验证下游产品。
3. **隐私说明必须符合实际请求边界。** 写清上游遥测/实验被阻断、GitHub 稳定版本元数据检查、手动外链和本地日志/设置。不能把禁遥测写成完全离线，也不沿用“可在 UI 退出上游采集”的失实下游说明。
4. **贡献、问题与行为准则入口归属明确。**
   - CONTRIBUTING 区分向 fork 提交下游问题与把通用修复回馈上游。
   - issue 模板包含版本/commit SHA、构建渠道、设置、复现与脱敏日志；不强迫用户公开完整配置或个人信息。
   - PR 模板分别记录 build、format、自动化、Windows 人工场景和未测原因，不用一个“已手测”勾选掩盖验证缺口。
   - 核验阶段 1 已隔离上游 CLA，不在本阶段重新设计贡献许可。
   - 行为准则的实际负责方/联系渠道需要用户确认；不要擅自替换成上游联系人或把用户个人邮箱写入公开文档。缺少决策时明确留下待确认项。
5. **补一份简短的上游同步清单。**
   - 先确认 remote、上游分支和最近合入 SHA，再比较变化；保留用户工作区及已发布 master 历史。
   - 同步后重点核对隔离、默认值/迁移、会话选择、资源生命周期与发布仓库限制，再运行对应测试。
   - 本阶段只编写流程，不顺带执行同步、自动合并、强推、删除功能或大范围格式整理。

## 验收

- 检查所有新增/修改文档的相对链接、路径、命令和相互引用。
- 逐项比对相关代码/测试，不以另一份文档作为唯一事实来源。
- 用户能区分上游产品与下游构建、历史快照与当前行为、已测与未测。
- 只改本阶段文档/模板所需内容；完成最终差异检查。对未运行的 build、format 或桌面检查如实说明，不把 Markdown 校验称为应用测试。

按共用格式交付并停止，不进入阶段 6。
